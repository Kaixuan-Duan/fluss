# 临时表/分区方案讨论

## Motivation

在 Fluss 的数据湖/流处理场景中，存在两个核心需求：

1.  场景一：历史数据迁移。创建一张隐藏的临时表/分区，写入全部历史数据后交换为正式表/分区，在数据写入完成之前，临时表 / 分区对 ListTables / ListPartitionInfos 不可见，确保不会被 Source 发现、枚举，导致用户读到中间态数据。

2.  场景二：INSERT OVERWRITE 数据重刷。为已有正式表创建一个临时表/分区，重刷数据到临时表 / 分区后，执行 Publish ，正式表指向重刷后的新数据。


在本文中，场景一为无同名正式表的情况，场景二为有同名正式表的情况。

## 元数据设计

### A. ZK 元数据、Assignment、DFS 物理路径

本方案不改变现有 ZK 路径结构。为便于理解元数据布局，先给出完整结构。

以分区表 `db1.t1`（tableId=1001，分区 `p1` partitionId=2001）为例：

```plaintext
1. ZK 元数据树

/metadata/databases/
  └── {db}/tables/
            └──{tableName}                          # TableRegistration JSON: tableId、bucketCount、bucketLayoutEpoch、createdTime, modifiedTime 等
                  ├── schemas/{schemaId}            # Schema JSON (schemaId=1)
                  └── partitions/{partitionName}    # PartitionRegistration JSON: tableId, partitionId, bucketCountActual 等


2. TabletServer Assignment 树

/tabletservers/
  ├── tables/
  │   └── {tableId}                                 # TableAssignment JSON
  └── partitions/                                   
      └── {partitionId}                             # PartitionAssignment JSON


3. DFS 物理路径树

{dataDir}/{dbName}/
  └── {tableName}-{tableId}/                        # 表级目录, 例如 t1-1001/
      └── partitions/                                
          └── {partitionName}-{partitionId}/        # 分区级目录, 例如 p1-2001/






```

**ZK 元数据**：`{tableName}`、`{partitionName}` znode 节点数据存储注册信息。

*   `{tableName}` 存储 `TableRegistration`

*   `{schemaId}` 存储 `Schema`

*   `{partitionName}` 存储 `PartitionRegistration`


**TabletServer Assignment**：`{tableId}` / `{partitionId}` znode 节点数据存储 bucket 到 TabletServer 的映射。

*   `{tableId}` 存储 `TableAssignment`

*   `{partitionId}` 存储 `PartitionAssignment`


**DFS 物理路径**：以 `{tableName}-{tableId}` / `{partitionName}-{partitionId}` 为目录。

*   TabletServer 重启时从 ZK 元数据中获取 `tableId` / `partitionId`，拼出 DFS 目录路径，定位并恢复数据。


---

#### A.1 历史数据迁移（无同名正式表）

创建一张隐藏的临时表/分区，写入全部历史数据后转为正式表/分区，无同名正式表，/tables/{tableName} 节点顶层 tableId=-1 表示无正式表，其余字段为默认值。stagingTable 中存完整的临时表注册数据。

**临时表 publish 为正式表**

publish 前后，/tables/{tableName} 节点数据：

```json
{
  "tableId": -1,
  "bucketCount": 0,
  "bucketCountActual": 0,
  ...
  "stagingTable": {
    "tableId": 1002,
    "bucketCount": 8,
    "bucketCountActual": 8,
    ...
  }
}


```
```json
{
  "tableId": 1002,
  "bucketCount": 8,
  "bucketCountActual": 8,
  ...
  "stagingTable": {
    "tableId": -1,
    "bucketCount": 0,
    "bucketCountActual": 0,
    ...
  }
}


```

**临时分区 publish 为正式分区**

publish 前后，/partitions/{partitionName} 节点数据：

```json
{
  "tableId": 1001,
  "partitionId": -1,
  "bucketCountActual": 0,
  ...
  "stagingPartition": {
    "partitionId": 2002,
    "bucketCountActual": 8,       
    ...
  }
}

```
```json
{
  "tableId": 1001,
  "partitionId": 2002,
  "bucketCountActual": 8,
  ...
  "stagingPartition": {
    "partitionId": -1,
    "bucketCountActual": 0,
    ...
  }
}

```

**说明：**

*   stagingTable / stagingPartition 存储完整的临时表/分区注册数据（与顶层字段结构相同）

*   publish 操作 = 交换顶层与 stagingTable / stagingPartition 的全部数据。交换后顶层变为正式表/分区数据，stagingTable / stagingPartition 变为默认值（tableId=-1 / partitionId=-1）

*   Publish 是一次 ZK setData 操作，原子完成

*   一张正式表/分区限制只能一个临时表/分区


#### A.2 INSERT OVERWRITE（有同名正式表）

有同名正式表，为已有正式表创建临时表，重刷数据后执行 Publish。

**表级 Publish**

Publish 前后，/tables/{tableName} 节点数据：

```json
{
  "tableId": 1001,
  "bucketCount": 8,
  "bucketCountActual": 4,
  "bucketLayoutEpoch": 1,      // 发生过 alter bucketCount 4 -> 8
  ...
  "stagingTable": {
    "tableId": 1002,
    "bucketCount": 8,
    "bucketCountActual": 8
  }
}


```
```json
{
  "tableId": 1002,           // 交换
  "bucketCount": 8,          // 交换
  "bucketCountActual": 8,    // 交换
  "bucketLayoutEpoch": 1,    // 不交换
  ...
  "stagingTable": {
      "tableId": 1001,
      "bucketCount": 8,
      "bucketCountActual": 4,
    }
}


```

**分区级 Publish**

Publish 前后，/partitions/{partitionName} 节点数据：

```json
{
  "tableId": 1001,
  "partitionId": 2001,
  "bucketCountActual": 4,
  ...
  "stagingPartition": {
    "partitionId": 2002,
    "bucketCountActual": 8
  }
}


```
```json
{
  "tableId": 1001,
  "partitionId": 2002,       // 交换
  "bucketCountActual": 8,    // 交换
  ...
  "stagingPartition": {
    "partitionId": 2001,
    "bucketCountActual": 4
  }
}


```

**说明：**

*   Publish 后，顶层指向重刷后的新数据，stagingTable / stagingPartition 中存未重刷的旧数据

*   共享字段（comment、partitionKeys、bucketKeys、properties、customProperties、remoteDataDir 等）不交换，因为临时表和正式表共享这些字段

*   Publish 是一次 ZK setData 操作，原子完成

*   一张正式表/分区限制只能一个临时表/分区


#### A.3 元数据字段变更

**TableRegistration 变更**

*   新增 `stagingTable` 字段（`StagingTableRegistration` 类型，`@Nullable`）

*   `stagingTable` 为 `null` 表示无临时表

*   `stagingTable` 不为 `null` 时存储完整的临时表注册数据


**StagingTableRegistration 结构**

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| tableId | long | 临时表 tableId |
| bucketCount | int | 临时表 bucketCount |
| bucketCountActual | int | 临时表 bucketCountActual |

> 以上字段与 `TableRegistration` 的差异字段相同，共享字段（`comment`、`partitionKeys`、`bucketKeys`等）不存放在 `StagingTableRegistration` 中，临时表直接复用顶层 `TableRegistration` 的值。

**PartitionRegistration 变更**

*   新增 `stagingPartition` 字段（`StagingPartitionRegistration` 类型，`@Nullable`）

*   `stagingPartition` 为 `null` 表示无临时分区

*   `stagingPartition` 不为 `null` 时存储完整的临时分区注册数据


**StagingPartitionRegistration 结构**

| 字段名 | 类型 | 说明 |
| --- | --- | --- |
| partitionId | long | 临时分区 partitionId |
| bucketCountActual | int | 临时分区 bucketCountActual |

反序列化兼容

*   旧版本 ZK 数据无 `stagingTable` / `stagingPartition` 字段，反序列化时默认为 `null`

*   新版本写入 `stagingTable=null` 等同于旧版本数据，向后兼容


## Public Interfaces

### 1. 新增 RPC

### 新增 RPC 方案 A

本方案新增 **6 个** RPC：

| 新增 RPC | 用途 | Request 字段 |
| --- | --- | --- |
| CreateStagingTable | 创建临时表 | table\_path + optional table\_json + ignore\_if\_not\_exists |
| CreateStagingPartition | 创建临时分区 | table\_path + partition\_spec + bucket\_count |
| DropStagingTable | 删除临时表 | table\_path + table\_id（检查元数据不一致情况，ABA 问题） |
| DropStagingPartition | 删除临时分区 | table\_path + partition\_spec + partition\_id |
| PublishStagingTable | 转正式表 | table\_path + table\_id |
| PublishStagingPartition | 转正式分区 | table\_path + partition\_spec + partition\_id |

服务端根据 ZK 节点是否存在自动路由无同名/有同名正式表，客户端无需感知

Create 情况

*   `table_path`：指定表名

*   `table_json`：无同名正式表时需要（完整表信息，含 schema/properties 等），有同名正式表时其中部分数据不需要


Drop 情况

*   无同名正式表（顶层 tableId=-1）：删除整个 ZK 节点 + 临时表 TableAssignment + DFS 目录

*   有同名正式表：清空 stagingTable（setData）+ 删除临时表 TableAssignment + 临时表 DFS 目录


Publish情况

*   交换顶层与 stagingTable / stagingPartition 的全部数据，通过一次 ZK `setData` 原子完成。有无同名正式表两个场景下本质是同一个操作，都是交换顶层与 stagingTable /stagingPartition 的全部数据。


### 新增 RPC 方案 B

本方案思路：无同名正式表时复用现有创建 RPC（加标志位），有同名正式表时在 AlterTable 新增统一的 staging 信息，并新增 AlterPartition RPC。（避免为临时表/分区单独设计一套 RPC）

#### B.1 无同名正式表 → 复用创建 RPC

临时表/分区的创建复用现有 `CreateTable` / `CreatePartition`，新增标志位区分正式/临时：

| RPC | 新增字段 | 说明 |
| --- | --- | --- |
| CreateTable | `optional bool is_staging_table` | `true` 时创建临时表，服务端在 stagingTable 字段中写入注册数据，顶层保持 tableId=-1 |
| CreatePartition | `optional bool is_staging_partition` | `true` 时创建临时分区，服务端在 stagingPartition 字段中写入注册数据，顶层保持 partitionId=-1 |

> 客户端无需感知无同名/有同名正式表，服务端根据 ZK 节点顶层 tableId/partitionId 是否为 -1 自动路由。

**CreateTable 修改（新增 is\_staging\_table）：**

```proto
message CreateTableRequest {
    required PbTablePath table_path = 1;
    required bytes table_json = 2;
    required bool ignore_if_exists = 3;
    optional bool is_staging_table = 4;  // 新增：true 时创建临时表
}


```

*   `is_staging_table=false`（默认）：创建正式表（现有逻辑不变）

*   `is_staging_table=true`：创建临时表，服务端在 stagingTable 字段中写入注册数据，顶层保持 tableId=-1

*   `table_json`：完整表信息（含 schema/properties 等），无同名正式表时需要


**CreatePartition 修改（新增 is\_staging\_partition）：**

```proto
message CreatePartitionRequest {
    required PbTablePath table_path = 1;
    required PbPartitionSpec partition_spec = 2;
    required bool ignore_if_not_exists = 3;
    optional bool is_staging_partition = 4;  // 新增：true 时创建临时分区
}


```

*   `is_staging_partition=false`（默认）：创建正式分区（现有逻辑不变）

*   `is_staging_partition=true`：创建临时分区，服务端在 stagingPartition 字段中写入注册数据，顶层保持 partitionId=-1


#### B.2 有同名正式表 → 复用 AlterTable + 新增 AlterPartition

有同名正式表时，临时表/分区的创建、转正、删除操作复用 `AlterTable`（表级）和新增 `AlterPartition`（分区级），通过新增字段携带 staging 操作类型和数据：

| RPC | 操作 | 新增字段 | 说明 |
| --- | --- | --- | --- |
| AlterTable（复用） | createStaging | `staging_op` + `add_staging_table` | 携带 StagingTableRegistration 数据（bucketCount 等），写入 stagingTable 字段 |
| AlterTable（复用） | publishStaging | `staging_op` + `add_staging_table` | 携带 staging\_id 用于 ABA 检查，交换顶层与 stagingTable 的全部数据 |
| AlterTable（复用） | dropStaging | `staging_op` + `add_staging_table` | 携带 staging\_id 用于 ABA 检查，清空 stagingTable + 删除 TableAssignment + DFS 目录 |
| AlterPartition（新增） | createStaging | `staging_op` + `add_staging_partition` | 携带 StagingPartitionRegistration 数据（bucketCountActual 等），写入 stagingPartition 字段 |
| AlterPartition（新增） | publishStaging | `staging_op` + `add_staging_partition` | 携带 staging\_id 用于 ABA 检查，交换顶层与 stagingPartition 的全部数据 |
| AlterPartition（新增） | dropStaging | `staging_op` + `add_staging_partition` | 携带 staging\_id 用于 ABA 检查，清空 stagingPartition + 删除 PartitionAssignment + DFS 目录 |

**设计说明：**

*   `staging_op` 表示当前操作类型：createStaging（创建）/ publishStaging（转正）/ dropStaging（删除）

*   `add_staging_table` / `add_staging_partition` 携带 staging 数据：createStaging 时携带 StagingTableRegistration / StagingPartitionRegistration 数据（bucketCount 等），服务端据此创建临时表/分区；publishStaging / dropStaging 时携带 staging\_id 用于 ABA 检查

*   `AlterTable` 的现有字段（config\_changes, add\_columns 等）与 staging 操作互斥：一次请求要么修改正式表配置，要么操作临时表

*   `AlterPartition` 是通用分区修改 RPC（与 `AlterTable` 对齐），未来不限于临时表场景

*   复用 `AlterTable` 已有的 epoch check + 乐观锁 + ZK 事务框架


**AlterTable 修改（新增 staging 字段）：**

```proto
message AlterTableRequest {
    required PbTablePath table_path = 1;
    required bool ignore_if_not_exists = 2;
    repeated PbAlterConfig config_changes = 3;
    repeated PbAddColumn add_columns = 4;
    repeated PbDropColumn drop_columns = 5;
    repeated PbRenameColumn rename_columns = 6;
    repeated PbModifyColumn modify_columns = 7;
    // 新增：staging 操作
    optional int32 staging_op = 8;            // 0=createStaging, 1=publishStaging, 2=dropStaging
    optional PbAddStagingTable add_staging_table = 9;  // staging 数据（createStaging） / ABA 检查（publish/drop）
}


```

**AlterPartition proto 定义（新增，与 AlterTable 对齐）：**

```proto
message AlterPartitionRequest {
    required PbTablePath table_path = 1;
    required PbPartitionSpec partition_spec = 2;
    required bool ignore_if_not_exists = 3;
    repeated PbAlterConfig config_changes = 4;
    // 新增：staging 操作
    optional int32 staging_op = 5;                  // 0=createStaging, 1=publishStaging, 2=dropStaging
    optional PbAddStagingPartition add_staging_partition = 6;  // staging 数据（createStaging） / ABA 检查（publish/drop）
}

message AlterPartitionResponse {
}


```

*   与 `AlterTable` 结构对齐：`table_path` + `partition_spec` 定位分区，`config_changes` 修改配置

*   `staging_op` + `add_staging_partition` 与 `AlterTable` 的 staging 字段语义一致

*   是通用分区修改 RPC，不限于临时表场景


**PbAddStagingTable / PbAddStagingPartition 定义：**

```proto
message PbAddStagingTable {
    // createStaging 时携带：StagingTableRegistration 数据
    optional int32 bucket_count = 1;          
    optional int32 bucket_count_actual = 2;   
  
    // stagingTable.tableId
    optional int64 staging_id = 3;            
}

message PbAddStagingPartition {
    // createStaging 时携带：StagingPartitionRegistration 数据
    optional int32 bucket_count_actual = 1;   
  
    // stagingPartition.partitionId
    optional int64 staging_id = 2;           
}

```

*   createStaging 时：表携带 `bucket_count` + `bucket_count_actual`，分区携带 `bucket_count_actual`（对应 StagingTableRegistration / StagingPartitionRegistration 的差异字段，tableId / partitionId 由服务端生成，共享字段从正式表继承）

*   publishStaging / dropStaging 时：携带 `staging_id` 用于 ABA 检查


#### B.3 分区操作对齐

分区与表的操作完全对齐设计：

| 操作 | 表级 | 分区级 |
| --- | --- | --- |
| 无正式表创建临时 | `CreateTable` + `is_staging_table=true` | `CreatePartition` + `is_staging_partition=true` |
| 有正式表创建临时 | `AlterTable` + `staging_op=createStaging` | `AlterPartition` + `staging_op=createStaging` |
| 转正式 | `AlterTable` + `staging_op=publishStaging` | `AlterPartition` + `staging_op=publishStaging` |
| 删除临时 | `AlterTable` + `staging_op=dropStaging` | `AlterPartition` + `staging_op=dropStaging` |
| 修改正式 | `AlterTable`（现有） + `config_changes` | `AlterPartition`（新增） + `config_changes` |

### 2. 现有 RPC 变更

#### Request 变更

| RPC | 新增字段 | 说明 |
| --- | --- | --- |
| ListTables | `optional bool filter_staging` | `filter_staging=true`（默认）不返回临时表，`false` 同时返回临时表 |
| ListPartitionInfos | `optional bool filter_staging` | `filter_staging=true`（默认）不返回临时分区，`false` 同时返回临时分区 |
| CreateTable | `optional bool is_staging_table` | 方案 B：`true` 时创建临时表（无同名正式表场景） |
| CreatePartition | `optional bool is_staging_partition` | 方案 B：`true` 时创建临时分区（无同名正式表场景） |

> **注意**：GetTableInfo 和 MetadataRequest 不加 filter\_staging。GetTableInfo 是客户端主动指定表名查询，不会自动枚举，服务端发现有 stagingTable 自动返回。MetadataRequest 客户端用 table\_path 查询，服务端发现 stagingTable 存在时同时返回临时表的 metadata（含 bucket assignment），客户端按 tableId 匹配。CreateTable/CreatePartition 的 is\_staging 标志仅在方案 B 中使用；方案 A 不改这两个 RPC。

#### Response 变更

| RPC | 新增字段 | 说明 |
| --- | --- | --- |
| GetTableInfoResponse | `optional StagingTableInfo staging_table` | 服务端发现有 stagingTable 自动返回 |
| ListTablesResponse | `optional StagingTableInfo staging_table` | `filter_staging=false` 时返回 |
| ListPartitionInfosResponse | `optional StagingPartitionInfo staging_partition` | `filter_staging=false` 时返回 |

#### 老客户端兼容

**filter\_staging 兼容：**

*   老客户端不发送 `filter_staging` 参数（proto2 optional，不发送时 `hasFilterStaging()=false`）

*   `hasFilterStaging()=false` → 服务端默认行为：不返回临时表/分区

*   新客户端发送 `filter_staging=false` → 返回正式 + 临时表/分区


**Response 新字段兼容：**

*   老客户端遇到 Response 中未知的 field number 自动忽略

*   新字段默认值为空，不影响老客户端
